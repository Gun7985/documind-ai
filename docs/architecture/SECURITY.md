# 인증 및 보안 설계

## 신뢰 경계

브라우저와 사용자 입력은 신뢰하지 않는다. Spring Boot가 유일한 공개 애플리케이션 API이자 최종 인가 지점이며, FastAPI와 Ollama는 인증된 보안 터널 뒤의 내부 구성요소로 유지한다.

## 로그인 및 JWT 검증 흐름

1. React는 Supabase Auth의 공개용 URL과 anon/publishable key로 로그인한다.
2. Supabase Auth는 사용자 세션과 액세스 JWT를 발급한다.
3. React는 Spring Boot API 요청의 `Authorization: Bearer <JWT>` 헤더에 액세스 JWT를 보낸다.
4. Spring Security Resource Server는 신뢰한 Supabase issuer의 공개 키로 서명을 검증한다.
5. `iss`, `aud`, `exp`, `nbf` 등 필수 클레임을 검증하고 허용한 알고리즘만 사용한다. 키 회전은 JWKS 캐시 갱신으로 처리하며 서명 검증 실패 시 fail closed한다.
6. 검증된 `sub` 클레임을 내부 사용자 UUID로 변환한다. 요청 본문이나 쿼리의 사용자 ID를 권한 판단에 사용하지 않는다.
7. Spring Boot는 문서 ID와 `owner_id = sub`를 함께 조회해 소유권을 확인한다. 존재 여부 노출 방지를 위해 다른 사용자의 자원도 기본적으로 `404`로 응답한다.

토큰은 URL, 로그, 오류 응답 또는 분석 프롬프트에 포함하지 않는다. 브라우저의 토큰 저장 방식과 CSRF/XSS 대응은 Supabase SDK 권장 방식과 실제 배포 구조를 기준으로 구현 전에 검증한다.

## 설정과 비밀 구분

| 공개 가능한 클라이언트 설정 | 서버 전용 비밀/설정 |
|---|---|
| Supabase 프로젝트 URL | Supabase service-role key(사용 시) |
| Supabase anon/publishable key | DB 비밀번호 및 직접 연결 문자열 |
| Spring Boot 공개 API base URL | FastAPI 내부 인증 비밀 |
| 비밀이 아닌 UI 환경 표시 | 터널 자격 증명, 서명 키, 운영 토큰 |

- 공개 가능하다는 것은 권한 검사를 생략해도 된다는 뜻이 아니다. anon/publishable key는 RLS와 서버 인가를 전제로 한다.
- React에는 Supabase 프로젝트 URL, anon/publishable key, Spring Boot 공개 API base URL만 명시적 allowlist로 주입한다. 서버용 `.env` 전체를 React 빌드에 전달하지 않는다.
- React 빌드 도구가 클라이언트 환경변수로 노출하는 접두사의 변수에는 위 공개 allowlist만 둔다. 실제 접두사와 변수명은 프런트엔드 빌드 도구를 선정할 때 확정한다.
- React 소스, 정적 파일, source map, CI 로그에 서버 전용 값을 넣지 않는다.
- 배포 전 빌드 산출물에서 알려진 비밀 변수명과 실제 비밀 지문이 없는지 검사한다.

## Spring Security와 소유권 검증

- 인증이 필요한 모든 API에 기본 deny 정책을 적용하고 명시적으로 허용한 health endpoint만 예외로 둔다.
- 컨트롤러가 받은 자원 ID만으로 조회하지 않고 repository/service 쿼리에 검증된 사용자 ID를 함께 전달한다.
- 목록, 검색, 이력, 상태 조회, 수정, 삭제 및 재분석 모두 같은 소유권 규칙을 적용한다.
- 권한 검사는 서비스 계층에서 일관되게 수행하고 테스트로 사용자 간 IDOR를 검증한다.
- 관리자 기능은 MVP 범위 밖이며 암묵적인 관리자 우회를 만들지 않는다.

## Supabase PostgreSQL과 RLS

- RLS는 `owner_id = auth.uid()` 정책을 통해 직접 데이터 접근에 대한 심층 방어를 제공한다.
- Spring Boot의 소유권 검사가 공개 API의 주된 통제다. RLS 우회 권한을 가진 서버 자격 증명을 사용할 경우에도 모든 서버 조회에 소유자 조건을 강제한다.
- 마이그레이션/관리 역할과 런타임 역할을 분리하고 런타임에 스키마 변경 권한을 주지 않는다.
- 자세한 테이블별 정책과 삭제 규칙은 [데이터 모델](ERD.md)을 따른다.

## private Storage 정책

- 원본 PDF는 public URL이 없는 private bucket에 저장한다.
- 객체 키는 서버가 생성한 `{owner_id}/{document_id}/source.pdf` 형태를 사용하며 사용자 파일명을 경로로 사용하지 않는다.
- 업로드, 다운로드, 삭제 전 Spring Boot가 문서 소유권을 확인한다.
- 직접 다운로드가 필요하면 소유권 확인 후 짧은 만료 시간의 서명 URL을 발급하며 로그와 분석 이력에 URL을 남기지 않는다.
- Storage 정책도 사용자 자신의 경로만 허용한다. service role 사용 시 이 정책을 우회할 수 있으므로 서버 검사가 필수다.

## Spring Boot ↔ FastAPI 내부 인증

- FastAPI는 인증된 보안 터널의 내부 주소에서만 접근 가능하게 하고 공용 인터넷에 직접 바인딩하지 않는다.
- 터널의 접근 정책에 더해 애플리케이션 계층 인증을 적용한다. 후보는 단기 서명 요청 또는 회전 가능한 고엔트로피 서비스 토큰이며 제품 선정 후 확정한다.
- 요청에는 작업 ID, 문서 식별자, 만료 시각, nonce/요청 ID를 포함하고 HTTPS 보호, 짧은 유효기간 및 재전송 방지를 적용한다.
- 공유 비밀은 양쪽의 비밀 저장소에만 두고 Git, React, URL 및 로그에 두지 않는다.
- FastAPI는 필요한 분석 요청만 허용하고 임의 파일 경로나 Ollama 프록시 기능을 제공하지 않는다.
- Ollama는 loopback 또는 제한된 로컬 네트워크에만 바인딩하고 터널을 통해 직접 라우팅하지 않는다.

구체적인 터널 제품, 상호 인증 방식과 키 회전 절차는 배포 후보 환경에서 검증 후 확정한다.

## 파일 업로드 검증

- 초기 정책은 파일당 최대 10MB, 최대 30페이지이며 압축 해제/파싱 도중에도 한도를 적용한다.
- 확장자와 클라이언트 `Content-Type`만 신뢰하지 않고 PDF 시그니처와 안전한 파서 결과를 확인한다.
- 파일명에서 경로 요소와 제어 문자를 제거하고 서버 생성 객체 키를 사용한다.
- 암호화 PDF, 손상 PDF, 0페이지, 페이지 제한 초과, 텍스트가 없는 스캔 PDF를 안전하게 거부한다.
- 추출 텍스트와 메타데이터의 크기에도 상한을 둔다. 파서 작업에는 시간과 메모리 제한을 적용한다.
- 업로드 실패 시 임시 파일과 Storage 객체를 정리하고 원본 내용을 오류 응답에 포함하지 않는다.
- 악성 파일 검사 도입 여부와 PyMuPDF 격리 수준은 실제 호스팅 환경에서 검증한다.

## 로그와 오류 응답

- JWT, Authorization 헤더, 쿠키, API 키, 서비스 토큰, 서명 URL, PDF 원문 및 전체 AI 프롬프트/응답을 기록하지 않는다.
- 파일명과 이메일은 필요 최소한으로 마스킹하고 사용자 UUID도 운영 진단에 필요한 범위에서만 사용한다.
- 상관관계 ID, 작업 ID, 상태, 안전한 실패 코드와 처리 시간만 구조화해 기록한다.
- 클라이언트 오류에는 안정적인 코드와 일반화된 메시지만 반환하고 스택 추적, SQL, 내부 URL 및 모델 원문을 노출하지 않는다.

## `.env`와 저장소 규칙 검토

- 현재 `.gitignore`는 `.env`, `.env.*`, 키 파일, 로그, 업로드 PDF와 테스트 비밀 디렉터리를 제외하고 `.env.example`만 허용한다.
- `.env.example`에는 실제 값 없이 설정 이름과 설명만 둔다. 예시 문자열이라도 실제 토큰 형식과 혼동될 값은 넣지 않는다.
- 루트 `.env.example`은 설정 이름의 문서이며 파일 전체를 React에 주입하지 않는다. Phase 2에서 프런트엔드용 공개 예시와 서버용 예시를 분리한다.
- 서버용 service-role key가 필요해지더라도 브라우저용 변수나 공용 예시값에 넣지 않고 별도 서버 비밀 이름으로 관리한다.
- 커밋 전 staged diff와 비밀 탐지 도구를 확인한다. 이미 노출한 비밀은 파일 삭제만으로 해결하지 않고 즉시 폐기·회전한다.

## 주요 보안 검증 항목

- 만료, 잘못된 issuer/audience, 변조된 JWT가 모두 거부되는가.
- 사용자 A가 사용자 B의 문서·작업·결과 ID를 사용해도 데이터가 노출되지 않는가.
- private Storage 객체가 서명 없는 URL로 노출되지 않는가.
- FastAPI와 Ollama에 공용 인터넷에서 접근할 수 없는가.
- 중복·재전송된 내부 요청이 새 분석을 만들지 않는가.
- 로그, 정적 React 번들 및 증빙에 비밀이나 PDF 본문이 없는가.
